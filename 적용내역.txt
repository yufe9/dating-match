적용내역 — 소개팅 매칭 로직 (dating-match)
작성일 2026-10-21 · 이 문서의 숫자는 match.py 의 상수와 실제 실행 결과에서 읽어 썼습니다.

================================================================
1. 프로젝트 소개와 실행 방법
================================================================
소개팅 '앱'이 아니라 '매칭 로직' 수업 과제입니다. 번호 하나를 넣으면 반대 성별 중 추천 상대와
그 상대를 고른 과정·이유를 콘솔에 보여 줍니다. 인물 70명은 모두 가상 인물입니다(men.csv, women.csv).

  설치: pip install -r requirements.txt      (sentence-transformers 하나)
  실행: python match.py M01                  (한 사람: 1~4단계 + 의외의 궁합 + 시즌)
        python match.py all                  (70명 전원의 1위)
        python match.py check                (자체 점검 + 시각화 기준값 + 질문 검색 답 점검)
        python match.py ask                  (질문 검색 화면 docs/ask.html 의 답 docs/ask.json 만들기)
  웹: docs/ask.html (매칭 로직 검색) — 로컬에서는 python -m http.server --directory docs 후 /ask.html
  API 키 없이 동작하고, LLM을 부르지 않습니다. 임베딩도 내 컴퓨터(CPU)에서 계산합니다.

================================================================
2. 매칭 로직 4단계 (match.py 코드 기준)
================================================================
[1 거르기 — 규칙]  filter_candidates()
  - 본인·같은 성별 제외 후, 아래 조건 중 하나라도 걸리면 제외합니다.
  - 양방향 검사: 나→상대(내 조건)와 상대→나(상대 조건)를 모두 봅니다.
  - 조건 6개: 희망 나이 / 흡연 / 종교 일치 / 자녀 계획 일치 / 같은 시 거주 / 희망 키
      · 희망 나이: 희망나이_최소~최대 밖이면 제외
      · 흡연: 흡연상대=불가인데 상대가 가끔·흡연
      · 종교 일치: 종교일치=필수인데 종교가 다름
      · 자녀 계획 일치: 자녀계획일치=필수인데 원함↔원치않음 (모름은 통과)
      · 같은 시 거주: 희망거주=같은시만인데 거주_시가 다름
      · 희망 키: 희망키_최소~최대 밖이면 제외 (적은 경우만)
  - 통과자가 0명이면 "조건에 맞는 사람이 없습니다"와 가장 많이 거른 조건을 안내하고 2~4단계를 건너뜁니다.

[2 후보 추리기 — 로컬 임베딩]  load_embeddings(), shortlist()
  - 모델: intfloat/multilingual-e5-small (내 컴퓨터 CPU에서 계산, 첫 실행 때 한 번 내려받음)
  - 임베딩에 넣는 문장 (embed_text):
      return (f"query: {p['자기소개']} 관심사: {', '.join(_list(p['관심사']))}. "
      f"주말: {p['주말스타일']}. 결혼 의향: {p['결혼의향']}. 자녀 계획: {p['자녀계획']}.")
    → 자기소개 + 관심사 + 주말스타일 + 결혼의향 + 자녀계획. e5 규칙대로 양쪽 모두 "query: "를 붙입니다.
  - 정규화한 벡터의 내적(= 코사인 유사도) 상위 K = 10명을 3단계로 넘깁니다.
  - 저장: embeddings.json 에 벡터와 내용 해시를 저장해, 프로필이 바뀐 사람만 다시 계산합니다(.gitignore 제외).
  - 모델을 못 불러오면 이유를 한 줄 알리고 통과자 전원을 3단계로 넘깁니다.

[3 순위 — 규칙 점수 100점]  rule_score(), rank()
  항목        배점  계산
  가치관       20   결혼의향 같으면 10, 한 칸 차이 5 / 자녀계획 같으면 10, 한쪽이 모름이면 5
  생활습관     20   음주·운동·주말스타일·반려동물 각각 같으면 5, 한 칸 차이 2 (반려동물 키움↔싫음은 0)
  관심사       20   겹치는 관심사 1개당 5, 최대 20
  성격·소통    10   연락빈도 같으면 6, 한 칸 차이 3 / MBTI 같은 자리 글자 1개당 1
  나이         10   차이 0~2세 10, 3~5세 6, 6세 이상 3
  거주지       10   같은 구 10, 같은 시 6, 다르면 2
  외모스타일    5   선호 키워드와 상대 외모스타일이 하나라도 겹치면 5 (선호가 빈칸이면 충족)
  경제·학력     5   희망연봉_최소구간 이상(빈칸이면 충족) 3 + 학력 차이 한 단계 이내 2
  - 선호에 기대는 항목(외모스타일·경제·학력)은 나→상대, 상대→나 양방향 평균이라 2.5점 같은 값이 나옵니다.
  - 동점 처리: 총점 → 가치관 → 생활습관 → 번호 순. 코드: rows.sort(key=lambda r: (-r["총점"], -r["점수"]["가치관"], -r["점수"]["생활습관"], r["상대"]["번호"]))
  - 외모·연봉 배점을 작게 둔 이유: 배우자 조건 1순위는 성격이고, 오래가는 관계는 가치관·생활습관이 좌우하기 때문입니다.

[4 이유 설명 — 규칙]  explain()
  - 1위의 항목별 점수표를 보여 주고, 점수가 높은 3개 항목(동률이면 만점 대비 비율이 높은 항목)으로 한 문장을 만듭니다.
  - 항목마다 정해진 문장 틀(_phrase)에 실제 값을 넣습니다. 지어내는 부분이 없습니다.
  - 예) M01 → 1위 W01 은하랑 91점:
        결혼 시기와 자녀 계획이 같고(20/20), 생활습관(음주·주말스타일·반려동물)이 같고(17/20), 관심사 3개(등산·요리·여행)가 겹칩니다(15/20).

3. 질문 검색 화면 (docs/ask.html)
================================================================
  - 70명 중 한 명을 고르고 돋보기 검색창을 누르면 질문 목록이 열립니다. 글자를 치면 목록이 걸러지고,
    질문을 누르면 그 사람의 매칭 결과로 만든 답(문단·단계·점수 막대·표)이 나옵니다.
  - 답은 전부 match.py 의 ask_answers() 가 1~7단계 결과로 만든 값입니다(python match.py ask → docs/ask.json).
    화면은 그 값을 그대로 보여 주기만 하므로 콘솔과 숫자가 같습니다. 언어 모델은 쓰지 않습니다.
  - 질문 11개 (ASK_QUESTIONS):
      1. 로직 확인하기
      2. 왜 1위가 잘 맞아?
      3. 2위와 뭐가 달라?
      4. 점수가 가장 낮은 항목은 왜 낮아?
      5. 누가 왜 걸러졌어?
      6. 임베딩 순위와 최종 순위는 왜 달라?
      7. 의외의 궁합은 누구야?
      8. 점수표는 어떻게 계산돼?
      9. 외모·연봉 점수는 왜 작아?
      10. 둘이 첫 데이트로 뭘 하면 좋을까?
      11. 이번 시즌엔 어떻게 됐어?
  - 데이트 제안은 둘 다 좋아하는 관심사 → DATE_IDEAS(관심사 32종) + 주말·음주 습관 규칙으로 고릅니다.
  - 점검(python match.py check): 70명 × 질문 11개가 모두 있는지, 1위 답의 이름·총점이 3단계 결과와 같은지,
    CSV의 모든 관심사에 데이트 제안이 있는지 확인합니다.
  - 예) M01 "왜 1위가 잘 맞아?" → 은하랑은 강한결님의 1위, 규칙 점수 91/100점입니다. 문장 유사도로는 1위였습니다.

[시험 1 — 질문별 근거만 주는 방식 (계획한 구조)]
  근거 = 나·1~3위 프로필, 항목별 점수와 이유 문장, 겹치는 관심사, 거르기·임베딩 요약 (1,613토큰)

  실측: 첫 질문 34.2초(모델 로드 4.1초 + 입력 처리 15.4초) / 이후 5.3~20.0초
        출력 13.2~14.0 토큰/초 · 입력 처리 105 토큰/초 · 첫 글자 2.6초(두 번째 질문부터)
        LLM 프로세스 메모리 1.98GB (시스템 전체는 다른 앱 포함 12.7GB → 최대 14.57GB)
  지어내기 시험 (M01 × W01, 질문 5개): 5회 중 3회 근거에 없는 사실
    · "2위와 뭐가 달라?" → "은하랑은 운동 주3회" (실제: 은하랑 주1~2, 주3이상은 M01)
    · "생활습관 점수가 만점이 아닌 이유는?" → "은하랑은 주말을 밖으로" (실제: 반반. 감점은 운동 한 칸 차이뿐)

    · 제대로 답한 예: "1위 상대의 연봉과 키는?" → "근거에 명시되어 있지 않습니다"
  판정: 속도는 기준(60초) 안, 지어내기는 기준(5회 중 2회 미만) 초과

[시험 2 — 프로젝트 설명 + 70명 전원 데이터를 모델에 넣은 커스텀 모델 (Ollama Modelfile)]
  넣은 양: 시스템 지시 21,306자 (약 11,700토큰), num_ctx 20480
  A(70명 + 질문별 근거): 첫 질문 340.4초, 이후 33~83초, 출력 3.9~4.0 토큰/초, 지어내기 3/5 이상
     예) 은하랑 키 "160cm"(실제 163), 2위를 W05·3위를 없는 인물 "W24 승가윤"으로 말함
  B(70명만):            첫 질문 291.8초, 이후 12~77초, 출력 4.3~4.5 토큰/초, 지어내기 4/5
     예) 은하랑 관심사 "베이킹·카페·봉사활동"(실제 요리·여행·등산·전시회), 생활습관 "20점"(실제 17)
  LLM 프로세스 메모리 최대 3.35GB
  판정: 데이터를 많이 넣을수록 느려지고(첫 답 5분) 다른 사람의 값을 섞어 더 많이 지어냄

[시험 3 — 질문 종류별 짧은 근거 + 문장 단위 검사기 (같은 질문 6종 × 3명 = 18문항)]
  코드가 질문 종류를 가리고 필요한 사실만 이름을 붙여 미리 비교해 주고, 답의 숫자·이름·관심사·생활습관이
  근거와 맞는지 한 문장씩 검사해 틀린 문장이 나오면 점수표 답으로 바꾸는 방식.
  exaone3.5:2.4b  검사 통과 13/18, 첫 질문 26.2초, 이후 최대 19.4초(평균 9.8초) — 검사를 빠져나간 틀린 문장 있음
                  (예: 2위의 관심사 점수를 15점이라고 함, 실제 10점)
  qwen3:4b-instruct-2507  검사 통과 16/18, 첫 질문 32.6초, 이후 최대 29.5초(평균 14.4초) — 더 정확하지만 느림,
                  '가장 낮은 항목'을 비율이 아닌 점수로 잘못 고른 답 2개
  기준(틀린 사실 0건 · 통과 80% 이상 · 이후 질문 15초 이내)을 함께 만족한 조합은 없었습니다.

[제외 이유]
  1. 2.4B 모델이 세 사람 이상의 프로필이 섞인 근거에서 '누구의 값인지'를 자주 헷갈렸습니다.
     과제 제출물에 틀린 사실을 말하는 해설을 넣으면, 코드가 정확히 계산한 결과보다 신뢰를 떨어뜨립니다.
  2. 70명 데이터를 통째로 넣는 방식은 정확도와 속도가 모두 나빠졌습니다.
  3. 7.8B 모델은 이 PC에서 질문당 60초를 넘을 것으로 추정되어 시험하지 않았습니다.
  4. 4단계 '이유 설명'은 이미 코드가 점수표에서 직접 만들고 있어, LLM이 없어도 설명 기능은 유지됩니다.
  → LLM 연결 코드는 넣지 않았고, 질문과 답은 3번의 질문 검색 화면이 규칙으로 보여 줍니다.
     Ollama 는 노트북을 켤 때 자동으로 실행되지 않게 꺼 두었습니다(시작 앱 '사용 안 함').

  높음  --llm 을 번호 앞에 쓰면 번호로 읽힘            → 인자에서 --llm 을 먼저 빼는 방식으로 막았음
  높음  파이프 출력이 cp949 라 특수 문자에서 종료       → LLM 답만 errors="replace" 로 출력하도록 막았음
  높음  Ollama 없음·꺼짐·시간 초과로 멈춤              → 모든 오류를 'LLM 사용 불가'로 바꾸고 점수표 이유를 보여 줌
  중간  질문 입력이 번호 입력·all 모드와 섞임          → 한 사람 모드에서만 질문, 입력 끝(EOF)이면 종료
  낮음  같은 입력 같은 순위 assert                     → LLM은 순위 계산 뒤에만 호출, 순위를 돌려주지 않음
  중간  Windows CRLF 로 diff 번짐                       → Edit 도구로만 수정, 이 문서는 LF 로 저장
  중간  지어내기                                       → 시험 결과 기준 초과 → 적용하지 않음
